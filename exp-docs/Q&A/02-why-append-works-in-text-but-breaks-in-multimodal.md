# Q&A 02：为什么纯文本 LatentMAS "append 就行"，多模态却有位置编码问题

> **日期**：2026-08-03 · **模式**：问答
> **问题来源**（用户原述）：你说纯文本模型天然成立，我理解是因为纯文本 LatentMAS 一个接一个 append 在 past key 后面，所以不需要考虑位置编码问题？那么多模态为什么会有这个问题？
> **证据基础**：卡 2 实测（[phase1-results.md](../VMAS-latent-collab/phase1-results.md)）、B1 验收（[phase2-results.md](../VMAS-latent-collab/phase2-results.md)）
> **对应原文档回填**：[phase1-cards-explained.md](../VMAS-latent-collab/phase1-cards-explained.md) §5 选段已就地精化

---

## 一句话答案

不是"不需要考虑位置编码"，而是"**默认的猜号规则在纯文本下恒好命中真值**"——这个区分正是多模态出问题的钥匙。

## 一、append 这个动作本身不带位置

位置不是写在 KV 上的标签，是 forward 时按"这个 token 排第几号"现场旋转进 Q/K 的（见 [phase1-cards-explained.md](../VMAS-latent-collab/phase1-cards-explained.md) §5 深入一层）。**每次 append，模型都必须给新 token 定号码**——这一步从没被跳过，只是纯文本下感觉不到。感觉不到，是因为 HF 的默认猜号规则极简单：

```
新 token 的位置 = past 的长度, past 长度+1, ...
```

## 二、纯文本"天然成立"的真正原因：一条恒等式

```
1D RoPE 恒等式:  第 N 个 token 的位置 ≡ N   (token 序号 = 位置号, 一一对应)
```

于是"past 有多长"这**一个数**完全决定下一个号码。猜号规则=恒等式 → **猜的永远等于真的**。"天然成立"的全部内容就是：不是位置不重要，是默认猜测在这个世界里**没有出错的可能**。

## 三、多模态坏在两处断裂

**断裂①：图像按"面"占位，token 数 ≠ 位置数。**
M-RoPE 里 12×12=144 token 的图只推进 12 格位置。卡 2 实测：A 段 **177 token、最大位置 44**。

> **追问回填：为什么推进 12 格，而不是 1 格（t 轴只占一个值）也不是 144 格（token 数）？**
> 规则：下一个文本 token 的位置 = **三轴上已用过的最大坐标 + 1**。图占用的坐标：t 轴 1 个**值**（144 个 token 共享同一 t；注意是"一个值"不是"一个 token"）、h 轴 12 个值、w 轴 12 个值 → 最大坐标由 h/w 推高 → **推进量 = max(1, 12, 12) = 12 = 网格边长**。
>
> 2×2 手算例：图占 t={2}, h={2,3}, w={2,3} → max=3 → 下一文本 token 从 4 起（推进 2=边长）。
>
> **为什么不能只跟 t 走（推进 1 格）**：那样图后第一个文本 token 的 h 坐标（st+1）会**小于**图第 3 行以后的 h 坐标（st+2…st+11）——按 mrope_section 分轴驱动的注意力头会读出矛盾的先后关系（t 轴上文在图后、h 轴上文在图中间）。max+1 保证图后文本**在三个轴上同时严格排在整张图之后**，每轴先后自洽。`MRopeTracker.max_pos` 记的正是这条规则。

```
默认猜号:  下一段从 177 起      ← "past 长度"还在, 但不再等于位置
真值:      下一段从 45 起
```

→ 卡 2 变体(b)：**认真执行"接着 past 长度数"也是错的**（Δlogit=19.3）。恒等式一断，cache 长度失去推出位置的资格。

**断裂②（更致命）：位置账本不随 past 传递。**
past_key_values 里只有**内容账**（每层已旋转的 K 和 V），没有**位置账**（"已用最大坐标"offset + 图的 grid_thw）。1D 时代 past 的长度本身就是位置账本（长度=下一位置）；M-RoPE 切断了这条捷径（长度≠位置），而真账本不在 past 里也推不出来。实测两种症状同根：文本续算（**有** input_ids+past）→ `get_rope_index` 算出段内 0,1,2,… 但 offset 缺失 → 从 0 重启（Δ=33.0）；latent 步（无 input_ids，连续向量**天生没有** token id——与 past 无关）→ 连段内计算都做不了 → [0,0,0]。**全程不报错。**

> **追问回填：是"用了 past 导致没有 input_ids"吗？**——不是，箭头要摆正。①latent 步没有 input_ids 是**本性**（伪 embedding 不是 token，天生无 id 可传），与 past 无关；②反例：A2 文本段**带着 input_ids+past** 照样从 0 重启——缺 id 不是根因；③真正根因=**位置账本（offset/grid）不在 past 里**，缺 id 只决定错的姿势（回退全 0 vs 段内从 0）。tracker 的本质=把这本不随 past 走的账在 Python 侧自己记（`max_pos`），逐段显式传 position_ids、旁路 HF 猜号。

## 四、账本类比

```
1D RoPE  = 单行流水号账本:  知道"前面记了 177 笔"→ 下一笔 178 号
M-RoPE   = (章,行,列) 三元组编号、插图占"一整面"而非"一串":
           光知道"前面 177 张纸"推不出下一页号——
           还得知道几张是图、图几乘几、当前最大坐标是多少
```

tracker 接管模块（B1）干的就是**自己记这本账**：维护"当前最大坐标"，文字按 max+1 三轴同值续、图按网格铺——把断裂②丢失的信息重新供上。卡 2 变体(c) 与 B1 验收的 top-1 100% 是账记对了的证明。

## 追问回填：是实现问题吗？M-RoPE 和 1D 的 VLM 实现不同？

三层答案：
1. **实现确实不同且实测四种**：1D 系（LLaVA-1.5/LLaVA-OV）走 HF 通用路径"cache 长度起接着数"→ KV 线程开箱即用（top-1 100%）；M-RoPE 系走专用 `get_rope_index` + `rope_deltas` 实例状态机 → 全败。且 Qwen2.5-VL 与 Qwen3-VL 是**两套不同实现**（后者源码自注改用 timestamp），病症一样——**家族级模式，非单个实现写坏**。
2. **但不是 bug，是契约外用法**：HF 的 M-RoPE 在承诺的工作流（单序列 generate：prefill 算位置存 deltas、decode 用 cache_position+deltas）里是对的；跨 agent 显式传 past 不在承诺范围，rope_deltas 缺失/陈旧 → 回退分支按"无账本"处理。静默因为回退分支本为别的场景而写。
3. **最深层：换谁实现都躲不掉**。1D 的幸运是数学性的（位置可从 cache 自带的标量=长度恢复）；M-RoPE 的位置取决于内容结构（图在哪、几乘几），K 旋转完成后该信息**原理上不可从 cache 恢复** → 任何正确的跨段实现都必须让账本随行：框架提供通道（HF 无公开契约）或调用方自己记（=MRopeTracker）。这是"接管模块是现代 VLM 必备适配器"framing 的完整论证链。

## 追问回填："金标准 3D 位置切片"（卡 2 P2c）是怎么做的

**不是弃用 latent、也不是纯文本 prefill**——图在、KV 线程在，唯一动的是给 B 段显式喂"正确答案的位置"：

```
P1: [A(图+文);B(文)] 一次性前向, hook 抓下 HF 内部算的整条 position_ids(3×L 矩阵)
    ——信息齐全(ids+grid 在场), 其计算定义上即正确答案, "金标准"由此得名
P2c: A 带图 prefill → past;  B 带 past 续算, 位置 = 从 P1 矩阵【切出 B 段那几列】
     (一行代码: pos_c = pid_p1[..., -LB:])
```

意义（控制变量）：三变体唯一差异是位置来源——猜(Δ33.0)/1D直觉(Δ19.3)/**真值(top-1 100%)** → 钉死"病灶只有位置，KV 内容无损"。

**局限的准确表述（追问修正）**：区分"程序"与"信息"——P2c 的**取数程序**（重跑全序列再切片）不可部署：要提前知道 B 内容、且整条重算令 KV 复用失去意义；但它需要的**信息**完全可实战获得：A 段前向时位置本就被正确算出（ids+grid 在场），**算出来、记下来（账本本质=一个 max 坐标标量）、下游从 max+1 续**即可——tracker 正是这个观察的工程化（`next_image_segment` 调公开的 `get_rope_index` 与内部计算同函数同结果；不用 hook 偷看是因为 hook 依赖内部结构、版本脆弱；实跑时连 A 段前向也显式喂 tracker 位置，账本与现实构造上同一）。B1 验收①判据 = tracker 位置与金标准切片逐位一致（实测 True）——两条路殊途同归。**准确定位：P2c 证明"位置是唯一的病且存在解"；tracker 不是复杂修复，是"把一个本该随 past 传递却被框架丢掉的标量自己带上"。**

（卡 2 主测试对象是文本续算，本就不含 latent 步；latent 位置坍缩是同脚本的独立测量。）

## 常见误读对照

| 误读 | 精确版 |
|---|---|
| "纯文本不需要位置编码" | 需要，且每步都在算；只是默认猜测恒中 |
| "多模态坏在三个轴太复杂" | 三轴本身没问题（文字 token 三轴同值退化成 1D）；坏在**图像占"面"打破 token数=位置数** + **续算时算位置的原料缺失** |
| "记得传连续位置就行" | 不行——连续位置的**起点**必须是 max 坐标+1，不是 past 长度（19.3 那个变体就是这么错的） |
